# image-library

Catalog, verify and de-duplicate a photo library spread over many drives, including
drives that are rarely connected or only readable from one operating system.

* **Many TB, resumable.** Every file is read once; progress is committed every second,
  so a crash, a reboot or Ctrl+C loses nothing. Run `imagelib scan` again to resume.
* **Drives come and go.** Each drive gets a small marker file, so it is recognised
  whatever letter or mount point it gets. Catalog data and previews stay available
  while it is unplugged. Unplugging mid-scan pauses that drive only.
* **Corruption found by decoding**, not by guessing: truncated files, zeroed or
  overwritten blocks (strict libjpeg-turbo checking catches damage Pillow silently
  repairs), RAW sensor data that is cut short or damaged, empty files, and the flat
  grey band of a partially written JPEG. Damaged files still get a preview for review.
* **Duplicates and look-alikes**: BLAKE3 for exact copies, perceptual hashes for
  resized copies such as thumbnails generated by old software.
* **Formats**: JPEG, PNG, TIFF (incl. 16-bit), HEIC/HEIF, PSD/PSB, camera RAW
  (CR2, CRW, CR3, NEF, ARW, DNG, ORF, RAF, … via LibRaw) and common video formats.

Nothing is ever deleted automatically. See [docs/PLAN.md](docs/PLAN.md) for the full
design and roadmap (GUI, thumbnail review, quarantine, multi-machine hub).

## Usage (development)

Requires [uv](https://docs.astral.sh/uv/). Released builds will be self-contained
downloads with nothing to install.

```sh
uv sync
uv run imagelib volume add /mnt/e --label "WD 2TB blue sticker"   # once per drive
uv run imagelib volume add /mnt/d --read-only   # never write to this drive (see below)
uv run imagelib scan /mnt/e            # scan a drive (or a folder inside one)
uv run imagelib scan                   # resume unfinished scans on connected drives
uv run imagelib scan --all             # rescan every connected drive (unchanged files are skipped)
uv run imagelib volume list            # drives, connected or not, with progress
uv run imagelib status                 # totals, corrupt files, duplicate space
uv run imagelib problems               # corrupt / suspicious files and where they are
uv run imagelib where ~/Desktop/x.jpg  # which drive holds this image (or look-alikes)
```

**Read-only drives.** Normally a drive gets a small `.imagelib-volume.json` marker
at its root. With `--read-only` nothing is ever written to the drive; it is recognised
by its filesystem serial number (the `XXXX-XXXX` Windows shows, which Linux also
reports for exFAT/FAT/NTFS) plus its capacity. Reformatting changes that identity,
and a cloned drive would share it, so prefer the marker where writing is acceptable.

The catalog lives in `%LOCALAPPDATA%\imagelib`, `~/Library/Application Support/imagelib`
or `~/.local/share/imagelib`; override with `--catalog DIR` or `IMAGELIB_HOME`.
It is two SQLite files: `catalog.db` (small; back it up) and `previews.db` (thumbnails,
roughly 10–80 KB per unique image depending on `--no-medium-previews`).

Try it on a generated library full of awkward cases:

```sh
uv run python tests/samplelib.py /tmp/sample-drive
uv run imagelib --catalog /tmp/sample-cat volume add /tmp/sample-drive --label Sample
uv run imagelib --catalog /tmp/sample-cat scan /tmp/sample-drive
uv run imagelib --catalog /tmp/sample-cat problems
```

## Tests

```sh
uv run pytest
```

Covers format coverage, corruption detection, duplicate and thumbnail matching,
rescans with changed/renamed/deleted files, FAT time-zone shifts, a drive unplugged
during discovery and during analysis, a hard crash mid-scan followed by resume, and
decoders that crash or hang on a malformed file.

## Performance notes

* One reader thread per drive (spinning disks hate parallel reads), different drives
  in parallel, and a process pool for decoding.
* On a 24-thread machine, analysis of 12 MP JPEGs runs at about 280 MB/s from cache,
  faster than a hard drive can deliver; 8 workers manage about 185 MB/s. Real Canon
  CR2/CRW files (20D to 6D) analyze in about 0.05 s plus about 0.13 s to verify the
  sensor data. Extra copies of already-catalogued content only cost a BLAKE3 hash.
* Memory is bounded: worker count follows RAM as well as CPUs, huge images reserve
  memory from a shared gate, and work pauses while free RAM is low.
* Scan from the OS the drive is attached to. Reading Windows drives from inside WSL
  measured about 20 MB/s in total, roughly 10x slower than native access.
* Unchanged files are skipped by size + mtime (100k files rescan in about a second).
